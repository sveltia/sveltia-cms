# End-to-end tests

These tests drive the whole app in Chromium with [Playwright](https://playwright.dev/): they sign in, browse, edit and save as a user would, and check the files the CMS writes. The unit and component tests mock the services around the code they test, so they can’t catch a flow that breaks between modules.

## Running

```bash
pnpm build      # the tests run against the production bundle in `package/dist`
pnpm test:e2e
pnpm test:e2e:ui  # Playwright’s UI mode, to watch and step through a test
```

To skip the build while working on a change, run the tests against the Vite dev server instead:

```bash
E2E_TARGET=dev pnpm test:e2e
```

The server listens on port 4180 and is started for each run. If the port is busy, e.g. because another worktree is running the tests at the same time, the run fails rather than test someone else’s server; set `E2E_PORT` to use another port. Each port has its own folder under `test-results/` for the traces, since a run clears its folder when it starts.

## How it works

- `server.js` serves the admin page in `site/admin/` and the bundle under `/dist/`. With `E2E_TARGET=dev`, the dev server is used instead, with `VITE_SITE_URL` pointing at itself.
- Every test answers the request for `config.yml` with its own config: `BASE_CONFIG` from `fixtures/test.js` by default, or another one set with `test.use({ config })`, either as an object or a YAML string.
- The config uses the `test-repo` backend, which keeps the repository files in the origin private file system (OPFS). Each test runs in a fresh browser context, so it starts with an empty repository.
- The `cms` fixture opens the admin page (`open()`), writes files to the repository before sign-in (`seed()`, which takes a string or a `Buffer` for each file), signs in (`signIn()`) and reads the files back (`readRepo()` for text, `readRepoFile()` for a binary file), so a test can check what a Save actually wrote.
- To test a Git backend, use `GITHUB_CONFIG` and ask for the `github` fixture: a `MockGitHub` from `fixtures/github.js` answers the GitHub REST and GraphQL requests from an in-memory repository and stores a session, so the CMS signs in on its own when the page opens. Commit to it as a colleague with `github.commit(files)`, read the branch with `github.readFile(path)`, and check the commits the CMS sent in `github.received`. `github.beforeCommit` runs once when the CMS next commits, to move the branch under it. `github.truncateTree = true` truncates the recursive file tree listing, as GitHub does for a huge repository, so the CMS has to list the folders one by one. A path added to `github.pathsWithoutHistory` has no commit history, as for a file deleted since the CMS listed it. A request the mock can’t answer fails the test and is listed in the error; teach the mock to answer it.
- The mock also keeps branches and pull requests, for Editorial Workflow: `WORKFLOW_CONFIG` in `fixtures/configs/workflow.js` turns it on. `github.commit(files, { branch })` commits to another branch, `github.readFile(path, branch)` reads one, and `github.refs` maps each branch to its head. A pull request in `github.pullRequests` has its `state`, `draft` flag and `labels`; `openEntryPullRequest()` opens one the way the CMS would, at the stage a test starts from. `github.mergePullRequest()` merges one as a colleague would. Like GitHub, the mock refuses a commit whose `expectedHeadOid` is out of date, a branch that already exists, and a merge that conflicts: a file both branches have changed since they parted.
- For Open Authoring, `OPEN_AUTHORING_CONFIG` in the same file turns the option on, and `github.canWrite = false` signs in as a contributor who can’t write to the repository. `github.createFork()` gives them a fork beforehand; without one, the CMS asks to make it, which `github.allowForking = false` refuses. The fork shares the commits and blobs of the repository, like a fork on GitHub, and its branches are kept in `github.refs` along with the others, keyed with its owner the way a pull request from a fork names its head: `github.forkBranch('main')` is `mona:main`. Use such a key with `github.commit()`, `github.readFile()` and as the `head` of `github.openPullRequest()`. `saveForkDraft()` saves an entry to the fork the way the CMS does, without a pull request. `github.createFork({ repo })` names the fork differently, so the CMS has to find it through the fork network. For the errors a contributor can meet while signing in, `github.canRead = false` hides the repository, `github.invitations` lists pending invitations, `github.scopes` sets the `X-OAuth-Scopes` header and `github.rateLimited = true` exhausts the rate limit. `github.forkDelay` makes a new fork answer 404 a few times, as GitHub is still copying it. Like on GitHub, a closed or merged pull request keeps the head it had then, even if its branch moves on. The Editorial Workflow specs are in `specs/workflow/`: the editor in `editorial-workflow.e2e.js`, the Editorial Workflow page in `board.e2e.js`, the options that shape the workflow in `options.e2e.js`, colleagues’ changes in `remote-changes.e2e.js` and Open Authoring in `open-authoring.e2e.js`.
- `github.canWrite = false` without Open Authoring signs in as a user with read-only access, who is refused, and `github.branchRule = { viewerCanPush: false }` protects the configured branch against the signed-in user, which makes the content that commits to it directly read-only.
- With `automatic_deployments` set in the backend config, the global toolbar has a Publish Changes button, which triggers a deployment with GitHub Actions: the mock lists the `repository_dispatch` event types it receives in `github.dispatches`. `specs/publish.e2e.js` covers it, along with a deploy hook set in the Settings dialog. `github.statusIndicator` sets the status GitHub reports, e.g. `major` for an incident the CMS shows above the app.
- GitLab and Gitea have mocks of their own: use `GITLAB_CONFIG` with the `gitlab` fixture, a `MockGitLab` from `fixtures/gitlab.js`, and `GITEA_CONFIG` with the `gitea` fixture, a `MockGitea` from `fixtures/gitea.js`. Like `MockGitHub`, they extend `MockGitRepository` from `fixtures/git.js`, which keeps the commits, branches and files, so `commit()`, `readFile()`, `received` and `beforeCommit` work the same way; `received` holds the bodies of the commit requests, in each API’s own format. Neither service guards a commit against a moved branch: GitLab refuses a change to a file whose last commit isn’t the one as of the `last_commit_id` the CMS sends, and Gitea one whose blob SHA isn’t the `sha` the CMS sends, so a colleague’s change only gets in the way when it touches the same file. `canWrite = false` refuses the user, `canPush = false` protects the branch, and `treePageSize` splits the file list into pages. `gitea.version` sets the version the instance reports: a Forgejo one, like `13.0.3+gitea-1.22.0`, makes the CMS read the files with the Forgejo API. `gitlab.statusCode` sets the status of GitLab.com, e.g. `500` for a major incident. Their specs are `specs/gitlab.e2e.js` and `specs/gitea.e2e.js`.
- `MockGitLab` also keeps merge requests for Editorial Workflow, which `specs/workflow/gitlab.e2e.js` covers: `gitlab.openMergeRequest()` opens one, with its status label and a `Draft: ` title prefix for a draft, and `gitlab.mergeRequests` lists them. GitLab has no draft field of its own, so the mock derives the `draft` it reports from the title, as GitLab does. A commit with a `start_branch` creates the branch, which GitLab refuses if it exists already, and `mergeBranch()` from `MockGitRepository` merges file by file, as `MockGitHub` does, so a conflicting merge is refused with 405 and a `conflict` merge status. `gitlab.pipelineRunning = true` keeps a merge request from being merged until `gitlab.finishPipeline()`, while the CMS sets it to be merged when the pipeline succeeds and checks every 10 seconds; install the clock to fast-forward through the wait.
- Open Authoring works on GitLab too, which `specs/workflow/gitlab-open-authoring.e2e.js` covers, and the mock models a fork the way `MockGitHub` does: `gitlab.createFork()` gives the contributor one, `gitlab.forkBranch('main')` is the `mona:main` key its branches are kept under in `gitlab.refs`, and `gitlab.allowForking = false` reports a project that can’t be forked. `gitlab.forkImportDelay` makes a new fork report an unfinished `import_status` a few times, as GitLab copies the repository in the background — where GitHub answers 404 instead. Two things only GitLab needs: a merge request carries the ID of the project its source branch lives in, so `openMergeRequest({ sourceProjectId: gitlab.forkProjectId })` opens one from the fork and `sourceProjectId: 99` one from some other project of the contributor’s, which the CMS has to ignore; and a commit to the fork carries a `start_project`, so the workflow branch starts from the configured project rather than the fork’s copy of it, which GitHub does by branching from the shared object store. Like GitLab, the mock finds that project by its ID or its plain path and answers 404 for anything else, such as a path URL-encoded the way it is in a request path. The mock answers the fork’s own `/repository/compare`, which is how the CMS works out what a draft holds, and the GraphQL blob query for the fork’s `fullPath`. A request for the fork before it exists is answered 404 on purpose, including at the project’s own name when the fork was renamed, so the CMS falls back to the fork list. `gitlab.mergeRequestPageSize` shortens the page of merge requests the mock returns, which stands in for a contributor with more of them in the project than the CMS reads at once: the entry’s own merge request is then missing from the board, and GitLab refuses a second one from its branch to the same target branch.
- `MockGitea` keeps pull requests for Editorial Workflow and Open Authoring as well, which `specs/workflow/gitea.e2e.js` and `specs/workflow/gitea-open-authoring.e2e.js` cover: `gitea.openPullRequest()` opens one, with a `WIP: ` title prefix for a draft, which the mock reads as the draft state the way the instance does, and `gitea.mergePullRequest()` merges one the way a maintainer would on the instance. The instance tracks a pull request’s head in a `refs/pull/{number}/head` reference, which the mock answers at `/git/refs/pull/{number}/head` — as a one-item list, like the instance, which treats the path as a prefix filter — and stops moving once the pull request is closed or merged. A Gitea list reads `head.sha` off that reference, while Forgejo, and a single pull request on Gitea, report the branch’s current head for as long as the branch exists — so a merged pull request on Forgejo says nothing about what was merged. The changed file list is worked out from the reference and from the merge base, stored at merge time for a merged pull request, and each file’s `contents_url` names the commit it was listed at. A merge carrying a `head_commit_id` is refused with 409 when the branch points elsewhere. The label filters behave as on the instance: the issue list takes label names but only matches an item carrying all of them, while the pull request list takes label IDs and matches any of them, listing an item once for each it carries. A comparison asked of the configured repository with a fork branch as its head fails with 500 on Gitea when the fork holds commits the repository doesn’t have — Gitea reads their files from the wrong repository — so the CMS compares a draft in the fork instead, which the mock answers too. `gitea.createFork()` gives the contributor a fork, kept under `mona:`-prefixed keys like `MockGitLab`’s; the fork is synced with `merge-upstream` on Gitea, which merges a fork that has moved on, and with `sync_fork` on Forgejo, which only fast-forwards and answers 400 otherwise, including when the fork is already up to date; a `GET` of the same path says beforehand whether a sync is allowed. `gitea.forkNameTaken` makes the fork request fail with 409 so the CMS asks again under another name, and `gitea.forksDisabled` turns forking off, which only Forgejo reports.
- A CI/CD provider’s builds are reported to a mock with `reportBuild(sha, builds)`: deployments, check runs and commit statuses on `MockGitHub`, and deployments and commit statuses on `MockGitLab`. The CMS looks them up to offer the deploy preview of an unpublished entry, which `specs/workflow/deploy-preview.e2e.js` covers. A build still running is checked again every 5 seconds; install the clock to fast-forward. Without a report, a commit has no build.
- For a self-hosted instance, configured with `api_root`, set the mock’s `apiRoot` before the page opens, and `graphqlURL` for GitHub and GitLab, as `specs/self-hosted.e2e.js` does for GitHub Enterprise Server, self-managed GitLab and a Gitea or Forgejo instance under a subpath. The CMS skips the status check of the hosting service for one, and reads a self-managed GitLab’s files in smaller batches. A Forgejo can report a bare version like Gitea 28 and later, so the CMS asks the Forgejo API for its version: `gitea.forgejo` says whether the mock is Forgejo when its `version` can’t tell.
- Each mock refuses a request that doesn’t carry its `token` with 401 Unauthorized, and answers the requests of every page in the browser context, including a sign-in popup; the `cms` fixture serves the config to every page too. `test.use({ signedIn: false })` makes the `github`, `gitlab` and `gitea` fixtures leave the session out, so the test starts on the sign-in page. `specs/sign-in.e2e.js` signs in with an access token, through an authenticator popup — whose page the spec serves, running the same `postMessage` handshake as Netlify’s or the Sveltia CMS Authenticator — and with the PKCE flow of Gitea and GitLab, where the spec answers the provider’s authorization page with a redirect carrying a code and its token endpoint with the mock’s token.
- `specs/local.e2e.js` covers Work with Local Repository, which the sign-in page offers for a Git backend on localhost. Playwright can’t pick a folder in the browser’s dialog, so the spec replaces `showDirectoryPicker()` with one returning the OPFS folder that `cms.seed()` and `cms.readRepo()` use, with a `.git` folder or file to mark it as a repository root. The CMS remembers the folder by storing its handle in IndexedDB, and reading an OPFS handle back from there closes the page in Playwright’s Chromium, so don’t reload the page while a folder is remembered.
- The CMS checks the repository for changes every minute, and when the window gets the focus back at least 10 seconds after the last check. Call `page.clock.install()` before opening the page, then `page.clock.fastForward()`, rather than waiting.
- `fixtures/configs/` holds larger configs with matching repository files to seed, e.g. `MONOLINGUAL_CONFIG` and `MONOLINGUAL_FILES`: a magazine site with most field types, a JSON collection referred to by a relation field, a file collection and a singleton. `MULTILINGUAL_CONFIG` and `MULTILINGUAL_FILES` are a travel magazine in French, English and Arabic, with English as the default locale although it isn’t listed first, and a collection for each i18n structure. Their specs are in a folder of the same name under `specs/`; `specs/multilingual/helpers.js` finds a locale’s pane and switches the locale shown in one. `specs/multilingual/folder-structures.e2e.js` has its own config for the structures that put each locale in a folder of its own: `multiple_folders`, `multiple_root_folders` and its deprecated name, and `omit_default_locale_from_file_path`. `specs/multilingual/i18n-options.e2e.js` covers `canonical_slug`, which links the translations of an entry when each has a slug of its own, and `omit_default_locale_from_preview_path`. `FIELD_TYPES_CONFIG` covers the remaining field types and the list and object options, with specs in `specs/fields/`. `MEDIA_CONFIG` and `MEDIA_FILES` have images in several media folders — the global one, a collection’s own and one next to each entry — for the specs in `specs/assets/`. `NESTED_CONFIG` has two nested collections, one in the `subfolders` mode and one of plain files with an index file; its specs are in `specs/structure/`. `COLLECTION_OPTIONS_CONFIG` and `COLLECTION_OPTIONS_FILES` have a collection for each option that restricts or shapes editing — `create` and `delete` turned off, `limit`, `reorder`, `filter`, `hide`, a divider, `slug` and `path` templates, `readonly` and `preview: false` — with specs in `specs/collections/`, which also check the `commit_messages` templates with the `github` fixture.
- `specs/collections/display-options.e2e.js` has its own config for the options that only change how a collection or a field is shown: a collection’s `icon` in the sidebar and a file’s in a file collection, a `description` with inline Markdown above the entry list, `preview_path_date_field`, which picks the DateTime field the date tags of `preview_path` come from, and a Select field’s `dropdown_threshold`. An icon is a Material Symbols ligature hidden from assistive technology, so check its text in the `.icon` element. Saving an entry goes back to the entry list, so open the entry again to check its updated “View on Live Site” link.
- `specs/app/` covers the app shell: the Settings dialog, the account and help menus, the Keyboard Shortcuts dialog, signing out, the Not Found page, the Create menu, search and the infobars. The production bundle fetches the UI strings for a language other than English from the CDN, and checks there for a newer version: the `cms` fixture answers the first with the file in `package/locales/` and the second with the version being tested. `specs/app/infobars.e2e.js` announces another version itself, and serves an admin page loading the bundle from the CDN without a version, the only kind of site the CMS offers to update.
- The CMS offers a few features only off localhost, like signing in on a phone. `test.use({ siteOrigin: 'https://cms.example.com' })` opens the admin page at that origin, passing its requests on to the test server; an HTTPS origin keeps the page a secure context. `specs/mobile/sign-in-link.e2e.js` checks the QR code to sign in on a phone by drawing the expected link with the `qrcode` package and comparing the modules, as Chromium can’t read a QR code on every platform, then opens the link in a second, phone-sized browser context sharing the GitHub mock. `serveSite()` from `fixtures/test.js` serves the site to such a context as the `cms` fixture does to the test page.
- `specs/mobile/` runs on a phone: `test.use({ ...PHONE })` from `specs/mobile/helpers.js` gives a screen under 768 pixels wide, with touch and no mouse. Sign in there with its `signIn(page)`, as `cms.signIn()` waits for the account menu button, which a phone doesn’t have. The bottom navigation replaces the global toolbar, a single tap opens an entry or an asset, and the editor shows one pane with a “Preview” toggle and a “Switch Locale” combobox.
- The view settings of the entry and asset lists are stored in IndexedDB for each repository, which the `test-repo` backend doesn’t have, so a test that reloads the page to check them uses `GITHUB_CONFIG`. They’re written in the background: wait for the stored value before reloading, as `specs/monolingual/entry-list-actions.e2e.js` does.
- `createPNG()` from `fixtures/files.js` makes a real image to upload, which the CMS can decode for its thumbnail.
- `specs/api.e2e.js` covers the JavaScript API a site extends the CMS with, added to the admin page with a `<script>` before or after the CMS one: `CMS.init()` with `window.CMS_MANUAL_INIT`, `registerEditorComponent()`, `renderRichText()`, `registerPreviewStyle()` and the event listeners. Add both scripts in one route, as a later route would fetch the original page again. The `CMS.init()` tests only run against the bundle, as the dev server starts the CMS on its own. A custom preview style renders the preview in an iframe, which `frameLocator()` reaches.
- `specs/formats.e2e.js` covers the entry file formats: TOML files, TOML and JSON front matter, a custom `frontmatter_delimiter`, the `output` options for YAML and JSON, and a Markdown collection without a `format`, which saves an existing entry in the front matter format it was read in and a new one with YAML front matter.
- `specs/app/page-setup.e2e.js` covers how a site sets up the admin page: config files linked with `<link rel="cms-config-url">`, and a custom `#nc-root` mount element; `specs/app/branding.e2e.js` covers `app_title` and `logo`. The `cms` fixture answers only `**/admin/config.yml?*`, so answer any other config file a link names with your own `page.route()`, keeping the `?*`, as the CMS appends a timestamp to the URL.
- `specs/assets/transformations.e2e.js` covers the media library’s `transformations` option, checking what a Save or an Upload writes: the `RIFF…WEBP` magic bytes of a converted image, and its size, decoded in the page with `createImageBitmap()`. SVGO and the HEIC decoder are loaded from UNPKG at runtime, so the spec answers those requests with `context.route()` from the copies in `node_modules`; the route also reaches the decoder’s Web Worker. The HEIC photo it uploads, `specs/assets/fixtures/teal-600x200.heic`, was made with `sips -s format heic` on macOS and is committed, as Linux has no such tool.
- `specs/save-errors.e2e.js` covers saving when the Git service fails: a server error, a dropped connection, a 502 Bad Gateway, which the CMS retries once on its own, a GraphQL error returned with 200 OK, a revoked token, and a commit GitLab refuses for a reason other than a colleague’s change. A `page.route()` takes precedence over the mock’s context route, so the spec routes only the commit request, GitHub’s `createCommitOnBranch` mutation or GitLab’s `POST …/repository/commits`, and calls `route.fallback()` for the rest; a failed commit never reaches the mock, which leaves `received` empty.
- `specs/collections/slug-options.e2e.js` covers the global `slug` options that decide the file name of a new entry — `encoding`, `clean_accents`, `sanitize_replacement`, `trim`, `maxlength`, `lowercase` and `timezone` — along with the deprecated collection `slug_length`, a `slug` template with date, field and transformation tags, and the number added to a duplicate slug. Each `describe` block serves a config with its own options; the titles mix accents, Japanese, emoji and punctuation, and each test checks the path a Save wrote and opens the entry again from the list.
- `specs/fields/rich-text-options.e2e.js` covers the options that shape the rich text editor of a `markdown` or `richtext` field: `modes`, `buttons`, `editor_components`, `linked_images`, `minimal`, `use_markdown_shortcuts`, `use_emoji_autocomplete`, `sanitize_preview` and `field_defaults.richtext`. In the `raw` mode, the field’s text box is the `<textarea>` holding the Markdown source, so check it with `toHaveValue()`. The block types, like Heading 2 or Code Block, are menu items of the “Show Text Style Options” menu button; a menu item’s text includes its icon name, so match it by role and name.
- `specs/fields/string-options.e2e.js` covers the options of a `string` field: the `email` and `url` types, checked when saving; `prefix` and `suffix`, which the input leaves out and the `type` and length checks strip, but the Save writes with any value that isn’t empty; the `before_input` and `after_input` labels, rendered as Markdown and never saved; and `minlength` and `maxlength` with the character counter, on a `string` and a `text` field. The counter has no role, so find it by its `aria-label`, like “No character entered. Maximum: 3.”, and match its text with whitespace between the numbers. Sveltia UI’s text input is always `type="text"`, so the `type` only shows in its `inputmode`.
- `specs/fields/list-options.e2e.js` covers the List field options that turn off or move its controls — `allow_add`, `allow_remove`, `allow_reorder`, `allow_duplicate` and `add_to_top`, which Clear and Restore Default in the field and editor options respect — for a list of objects, a list of strings and a list with types, along with `minimize_collapsed`, `collapsed: auto` on a list and an Object field, and `label_singular` in the Add button and the item count. A list only shows `label_singular` for a single item, e.g. “1 Photo” but “2 Gallery”. The Add button moves above the items with `add_to_top`, so the spec compares positions with `boundingBox()`.
- `specs/fields/generated-fields.e2e.js` covers the fields whose values the CMS generates or keeps out of sight: the UUID field with `prefix`, `use_b32_encoding` and the options that unlock it, the Hidden field’s template tags and values of other types, the Compute field’s `value` templates, also in a list, and the Code field’s languages, `output_code_only` and `keys`. It checks what each does for a new entry, an existing one, one saved before the field was added, and a duplicate. The Hidden field’s author tags need a signed-in user, so its tests use the `github` fixture. A Compute field is hidden in the editor, so check its value in the preview. A Code field passes on what was typed 100 milliseconds later, which a Save waits for, so the spec saves right after typing.

## Writing tests

- Name the files `specs/*.e2e.js`. Vitest ignores the `e2e` folder.
- Query by role and by the text a user sees, like the component tests do. Wait with web-first assertions (`await expect(locator).toBeVisible()`, `expect.poll()`), never with `waitForTimeout()`. The assertions retry for up to 5 seconds.
- An interpolated value in a label comes wrapped in bidi isolates, so match such a name with a regular expression: `getByRole('main', { name: /Posts.*Collection/ })`.
- Sveltia UI keeps closed dialogs and popups in the DOM with `inert`. Target the open one with `page.locator('dialog:not([inert])')`.
- Choose a menu item or a dropdown option with `cms.chooseMenuItem(trigger, item)`, and open a dropdown to type into with `cms.openPopup(trigger, popup)`. In a tree, like the path editor’s folder picker, click the label of a tree item rather than the item itself, which contains its children, so its centre can be on one of them.
- The editor renders each field only once it’s scrolled into view, so a field further down doesn’t exist yet for a locator. For a config with many fields, use a tall viewport, e.g. `test.use({ viewport: { width: 1280, height: 6000 } })`, as `specs/fields/` does.
- A short `select` or `relation` field is shown as a radio group and a longer one as a combobox, a `number` field as a spinbutton and a `boolean` field as a switch. A list item is moved with its “Reorder Item” handle and the arrow keys. A radio’s label is its accessible name, not its text content.
- The rich text editor of a `markdown` or `richtext` field can’t be filled in: click it and type with `page.keyboard.type()`. The End key doesn’t move the caret on macOS, so set the selection in `evaluate()` to put the caret at the end. The editor picks up a selection made with the mouse only when the browser fires `selectionchange`, so a shortcut pressed right after a double-click can find nothing selected; `selectText()` in `rich-text.e2e.js` sets the selection and fires the event.
- Pin a known bug with a test that asserts the current behaviour, named with “(known issue)” and commented with the issue and what to expect once it’s fixed. The test fails when the bug is fixed, telling you to update it. Don’t use `test.fail()`: it also passes when the test breaks for an unrelated reason, e.g. a renamed button.
- The `{{year}}`, `{{month}}` and `{{day}}` slug tags come from the time of saving, so pin the clock with `page.clock.install({ time })` in a test that checks a file name.
- Optional fields missing from a file are written as empty values when the file is saved, unless `output.omit_empty_optional_fields` is on.
- Open an entry by clicking its row. Navigating to its hash URL doesn’t open the editor after sign-in.
- A touch sent while a page transition runs lands on the document element and is lost. Before swiping, wait until `document.elementFromPoint()` returns the target, as `swipe()` in `specs/mobile/assets.e2e.js` does.
- Upload a file with `setInputFiles()` on the hidden `input[type="file"]` inside the field group, or wait for the `filechooser` event when a button opens the file picker. A synthetic `drop` is ignored, as its files can’t be read as file system entries; drop files with `cms.dropFiles()`, which has the browser drag them in from disk. Give each uploaded file distinct content, e.g. another `createPNG()` colour. The same file twice opens the conflict dialog, which then intercepts every click.
- With i18n, the second pane shows the preview until a locale is picked from its “Switch Locale” radio group. A locale that isn’t enabled for the entry is named like “French (disabled)”, and one with an error like “Arabic (error)”.
- Answer a translation service’s requests with `page.route()`, e.g. `https://translation.googleapis.com/**`; never call a real one. The API key the CMS asks for is kept in the browser, so a made-up key in the service’s format will do. `specs/multilingual/ai-translation.e2e.js` does the same for each AI service — Anthropic, OpenAI, Gemini, Mistral and DeepSeek — picked in the Settings dialog; they all take the texts as a JSON array in the prompt and return one, each in its own envelope.
- Answer a stock photo service’s requests with `page.route()` too, as `specs/assets/stock-photos.e2e.js` does: Lorem Picsum needs no API key, while the others take a made-up key in the service’s format.
- The cloud storage services have mocks in `fixtures/cloud/`, used by `specs/assets/cloud-storage.e2e.js`. `MockS3` is an Amazon S3 bucket, or one of an S3-compatible service like Cloudflare R2, which checks the AWS Signature Version 4 of every request by signing it again with its secret access key. `MockAzureBlobStorage` checks the SAS token in the query, `MockUploadcare` the keys in the `Authorization` header and the HMAC signature of an upload, and `MockCloudinary` serves the console’s sign-in page and media library widget, which talks to the CMS with `postMessage`. Each lists in `refused` the requests it turned down. They hold the objects in memory, add the CORS headers a bucket set up for the CMS would, and serve an object to anyone, like a public bucket, so the CMS can show it. Match a bucket’s URL with a function rather than a glob, which can’t be anchored to a host; a request that slips past reaches the real service, as S3 answers for any bucket name.
- If an interaction seems to be lost, e.g. a `fill()` that leaves the field empty, check what had the focus at that moment before adding a wait. A test that types faster than a user can still points at a real problem: the first test here found the “Create New Entry” button opening an empty popup that made the editor inert for a moment.
